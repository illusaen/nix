Plain Fleet Architecture

This document describes the flake-free architecture used by this Nix repository: how raw fleet data is normalized, how feature modules are resolved, how NixOS and Darwin systems are evaluated, and how deploy and CI entrypoints share the same API.

Design Goals

Plain Nix First

Routine evaluation, deployment, package access, and checks use ordinary Nix files. The legacy flake path can remain present during migration, but it is not the operational source of truth.

Data Before Modules

Hosts, users, services, fonts, themes, and package pins are plain data. Libraries normalize and validate that data before platform modules are imported.

Feature Ownership

A feature owns the NixOS and Darwin module fragments for one concern. Hosts select feature names, not module paths, and the resolver closes dependencies.

The steady-state architecture is intentionally small: npins fetches sources, default.nix assembles an API, and lib/* handles validation, routing, feature closure, host evaluation, and local packages.

API Surface

default.nix is the public interface for the plain architecture. Other entrypoints import it instead of reimplementing fleet loading or feature resolution.

Attribute Purpose Main Consumers
sources Pinned upstream source paths from npins. Feature modules, host builders, shell, package lib.
fleet Validated and routed fleet data. Feature modules, deploy selectors, inspection.
checks Combined boolean results from fleet tests, feature-local tests, graph checks, services, secrets, deploy selectors, and themes. bin/check, ci.nix.
libs Combined attrset of libs. Builds, checks, tests.
nixosConfigurations / darwinConfigurations Evaluated NixOS and Darwin configurations from fleet hosts. darwin.nix, ci.nix, targeted evals.
overlays Inject repo-local packages as pkgs.local. Host builders, features, deploys, cache builds.

Evaluation Pipeline

The plain graph has one direction of travel: pins and raw fleet data flow into validation, routing, feature resolution, and finally platform system builders. No host imports a feature file directly.

  1. npins/default.nix converts locked GitHub and GitLab pins into source paths.
  2. fleet/default.nix returns raw fleet data.
  3. fleetLib.assertValid rejects malformed hosts, users, groups, services, duplicate addresses, and missing host keys.
  4. serviceLib.servicesByHost returns routed service records by host name.
  5. featureLib.featuresByHost returns derived feature names by host name after services are attached.
  6. featureLib.modulesFor closes feature imports and returns the generic plus platform-specific module list.
  7. nixosConfigurations and darwinConfigurations expose evaluated hosts from NixOS eval-config.nix and nix-darwin eval-config.nix.

Feature Contract

Every directory under features/ may expose imports, platform modules, feature-local tests, and service secret metadata. The resolver discovers features from the filesystem and does not require a central registry. Feature imports can mix string feature dependencies with local file paths for splitting a large feature into smaller fragments. 

{
  imports = [
    "other-feature"  # Feature dependency.
    ./networking.nix # Local feature fragment.
  ];

  serviceSecrets = { service, serviceName, hosts }: [
    { secret = "shared/example.age"; hostName = service.primary; }
  ];

  tests.someInvariant = true;

  modules.generic = { fleet, host, user, sources, pkgs, lib, ... }: {
    # Shared options valid on NixOS and nix-darwin
  };

  modules.nixos = { fleet, host, user, sources, pkgs, lib, ... }: {
    # NixOS options
  };

  modules.darwin = { fleet, host, user, sources, pkgs, lib, ... }: {
    # nix-darwin options
  };
}

Feature Dependencies

String entries in imports list other feature names. The closure is stable and duplicate-safe: once a feature is seen it is not added twice. Host feature lists stay small because shared behavior can be implied by one parent feature.

Local Fragments

Path entries in imports are imported relative to the feature file and merged into the same feature. This is useful for files such as features/base/networking.nix that should contribute modules without becoming host-selectable features.

Platform Modules

modules.generic is prepended for every supported platform, while modules.nixos and modules.darwin are imported only for matching hosts. A feature can intentionally support only one platform; direct host references to unsupported features are caught by checks.

Injected Argument Meaning
fleet Validated, routed fleet data.
host The normalized host being evaluated, including host.services.
user The host owner user object plus an injected name.
sources All pinned source paths from npins.
fleetLib Shared fleet helpers such as POSIX group resolution.
packageLib Local package overlay and package helpers.

Host Builders

lib/hosts.nix is the boundary between fleet data and platform module systems. It builds a common host module, injects shared arguments, applies the local overlay, and then delegates to the platform evaluator.

Function Output
mkHostModule A module that imports the resolved platform feature modules, applies packageOverlay, injects special args, and asserts valid feature references.
mkNixosConfigurations An attribute set of evaluated NixOS configurations for Linux hosts.
mkDarwinConfigurations An attribute set of evaluated nix-darwin configurations for Darwin hosts.

Services and Secrets

Fleet services are declared once, then routed onto hosts. The service library assigns each selected host a role and appends the service feature name to that host. Service features read host.services to find routed service records by name and configure ports, role-specific behavior, persistence, and secret ownership.

Routing Rules

  • The primary host receives role = "primary".
  • Backup hosts receive role = "backup".
  • HTTP and HTTPS services are checked as TCP for port conflicts.
  • Base, boot, desktop, GPU, tagged program, preservation, and routed service features are derived for each host.

Secret Coverage

  • Service features expose serviceSecrets.
  • default.nix derives expected age secret names.
  • Checks verify declarations and recipient host keys.
  • Feature modules still own service-specific age.secrets.

Packages and Overlays

Local packages live under packages/*/package.nix. The package library discovers them by directory, exposes buildable package sets by system, and provides an overlay that makes each package available directly as pkgs.<name> and collectively as pkgs.local.<name>.

The overlay is also applied inside mkHostModule, so any feature can use local packages without importing the package library itself.

Deploy Flow

bin/deploy is the operational entrypoint. It uses the same selector logic exported by default.nix, splits hosts by platform, and dispatches NixOS hosts through Colmena and Darwin hosts through nix-darwin builds.

Command Behavior
bin/deploy --plan --on @all Prints selected hosts, platform, and target host without building.
bin/deploy --dry-run --on odin Runs Colmena dry-run for a NixOS host.
bin/deploy --build --on odin Builds the NixOS host and runs dix against the local current system when possible.
bin/deploy --apply --on odin Applies the NixOS host through Colmena.
Darwin support exists in the plain architecture, but remote Darwin activation remains an explicit design decision. Current Darwin apply builds locally and runs activation scripts from the build result.

Checks and Debugging

Checks are ordinary Nix booleans and derivations. default.nix exposes low-level checks; ci.nix aggregates those checks and asserts representative evaluated behavior for the current fleet.

Fast Local Checks

bin/check
nix-build ci.nix -A plain-eval --no-out-link
treefmt --verbose

Targeted Evaluation

nix-instantiate --eval --strict --json --expr '
let
  api = import ./default.nix;
  cfg = api.nixosConfigurations.odin.config;
in {
  hostName = cfg.networking.hostName;
  tailscale = cfg.services.tailscale.enable;
}'
Check Group What It Protects
Fleet validation Known owners, supported systems, target hosts, preservation disks, duplicate feature/tag values, host keys, duplicate addresses, duplicate UIDs.
Feature resolution Unknown host features, unsupported platform modules, service feature module availability, and feature-local unit tests.
Service routing Primary/backup route behavior in tests, service feature availability, and per-host port conflicts.
Secret coverage Required service secrets are declared and encrypted for the host keys that need them.
Configuration parity ci.nix asserts concrete evaluated NixOS and synthetic Darwin behavior.

Inspection

The API exposes the evaluated fleet and checks directly, so inspection can stay in Nix rather than relying on ad hoc text scraping. 

let api = import ./default.nix; in {
  odinServices = api.fleet.hosts.odin.services;
  failedChecks =
    builtins.filter (name: api.checks.${name} != true)
    (builtins.attrNames api.checks);
}

Design Rules

  • Add upstream inputs to npins/sources.json; import explicit source paths from features.
  • Add host-selectable behavior as a directory under features/.
  • Use imports in feature files for logical feature dependencies, not direct host imports.
  • Use serviceSecrets for service-owned secret declarations.
  • Put repo packages in packages/*/package.nix; consume them through pkgs.local.
  • Prefer targeted evals through api.nixosConfigurations and api.darwinConfigurations when debugging host behavior.
