Fleet Architecture Blueprint

A non-flake, Colmena-centered architecture for Linux hosts, with a matching Darwin deploy path, dendritic feature ownership, service primary/backup routing, agenix secrets, and CI-friendly tests.

Status: in progress Inputs: npins NixOS deploy: Colmena Darwin deploy: nix-darwin wrapper Secrets: agenix

Goals

Optimize for plain Nix

Stop using flakes as the primary interface, avoid copying the whole repository into the store for routine evaluation, and expose normal Nix entrypoints that can be called by CI, Colmena, and local scripts.

Keep features dendritic

A feature lives in one directory and owns its NixOS module, Darwin module, package hooks, secrets, tests, and service routing behavior. Hosts select feature names, not scattered module paths.

Use the right deployer

Colmena deploys NixOS hosts. Darwin hosts use nix-darwin through the same top-level deploy command, because Colmena's deployment options are NixOS module options and local deployment is NixOS specific.

Keep service routing explicit

Services declare a primary host and backup hosts. The resolver injects the routed service metadata into each host and imports the matching feature module for the host platform.

Top-Level Shape

The new architecture replaces flake-parts, gen-flake, and gen-schema with direct Nix files. The repository still uses Nix modules for NixOS and nix-darwin systems, but the fleet model is plain data plus a small resolver library. The plain entrypoints now exist; the remaining migration work is mostly parity, cleanup, and CI hardening. 

.

Evaluation Flow

The resolver is the only layer that interprets the fleet graph. It returns evaluated host contexts, Colmena nodes, Darwin configurations, and check derivations. Feature modules receive resolved fleet, host, user, and host.services through specialArgs.

Fleet Data Model

Fleet data is intentionally small. It should be easy to inspect in nix repl, validate in unit tests, and pass to host builders without hidden option machinery.

Host example

{
  odin = {
    system = "x86_64-linux";
    owner = "wendy";
    targetHost = "odin.home.arpa";
    tags = [ "desktop" "gpu:nvidia" ];
    features = [
      "base"
      "desktop-shell"
      "programs-core"
      "theming"
    ];
    monitors.main = "DP-2";
    preservation = {
      enable = true;
      disk = "nvme0n1";
    };
  };
}

The host platform is derived from system: Linux systems become nixos, Darwin systems become darwin.

Service example

{
  navidrome = {
    feature = "navidrome";
    primary = "odin";
    backups = [ "huginn" ];
    port = 8080;
    protocol = "http";
    secrets = [ "navidrome-env" ];
  };
}

References are names in data files. The resolver turns names into objects only when building a host context. This keeps registry files serializable and removes the need for reference types.

Dendritic Features

A feature owns every platform implementation in one place. A host does not import a NixOS path directly; it enables a feature name. The resolver picks the right module for that host platform. 

# features/navidrome/default.nix
{ inputs, lib, ... }:
{
  imports = [ "secrets" ];

  modules.nixos = { host, ... }: {
    services.navidrome = {
      enable = true;
      settings.Port = host.services.navidrome.port;
    };
  };

  modules.darwin = null;

  serviceSecrets = { hosts, ... }:
    map (hostName: {
      secret = "shared/navidrome-env.age";
      inherit hostName;
    }) hosts;

  tests.nixos = ./test.nix;
}
Feature field Purpose
imports Feature names this feature depends on.
modules.nixos NixOS module imported only for NixOS hosts.
modules.darwin nix-darwin module imported only for Darwin hosts.
packages Planned: optional package definitions or overlay hooks owned by the feature. The current resolver does not consume this field yet.
serviceSecrets Optional function returning routed age secret requirements for service features.
tests Optional feature-local boolean checks imported by the top-level unit test set with namespaced keys.

Service Routing

# lib/services.nix
routeServices = { hosts, services }:
  mapHosts (hostName: host:
    host // {
      services = servicesForHost hostName services;
      features = unique (
        host.features ++ routedServiceFeatureNames hostName services
      );
    });

The resolver must fail if a service routes to a host but the selected feature has no module for that host platform. This prevents registry drift and silent non-deployment.

Deployment Model

NixOS

hive.nix contains only NixOS hosts and is consumed by Colmena. Each node gets deployment metadata from the host registry: targetHost, targetUser, tags, and build policy. 

# hive.nix
let
  api = import ./default.nix;
in
  { meta = { ... }; } // api.deploy.nixosHosts

Darwin

darwin.nix exposes nix-darwin configurations. The deploy script builds the activation package and runs activation on the target host over SSH or locally. 

# darwin.nix
let
  api = import ./default.nix;
in
  api.hostLib.mkDarwinConfigurations {
    inherit (api) fleet sources;
  }

Single deploy API

bin/deploy --on odin
bin/deploy --on huginn
bin/deploy --on macbook
bin/deploy --on @server
bin/deploy --build-only --on @all

The script selects hosts from the registry. NixOS targets are grouped into one Colmena invocation where possible. Darwin targets are handled one host at a time with nix-darwin activation.

Secrets

Keep agenix as the default. It matches the existing host public key layout and decrypts secrets during activation on the target host. Colmena deployment.keys remains available for bootstrap or deploy-time generated keys, but application secrets should stay in agenix. 

secrets/
|-- secrets.nix
|-- hosts/<host>/host_ed25519.pub
|-- hosts/<host>/*.age
|-- services/<service>/*.age
`-- users/wendy/age.pub
  • Host-only secrets include the target host and admin recipients.
  • Service secrets include primary and backup host recipients.
  • CI validates that every referenced encrypted file exists.
  • CI validates that every service secret can be mapped to deployed hosts.

Developer Shell

Use shell.nix with npins sources. Do not keep numtide/devshell unless a later workflow needs it. The default shell should be boring and fast. 

# shell.nix
let
  sources = import ./npins;
  pkgs = import sources.nixpkgs { system = builtins.currentSystem; };
in
pkgs.mkShell {
  packages = with pkgs; [
    npins
    colmena
    agenix
    treefmt
    deadnix
    statix
    nil
    shellcheck
  ];
}

Library Recommendations

Library Recommendation Reason
npins Adopt Pins inputs without flakes and keeps source behavior explicit.
colmena Adopt for NixOS Fast, stateless NixOS deployment with host selection and tags.
nix-darwin Keep Required for Darwin system configuration and activation.
agenix Keep Small secrets surface area and fits existing SSH host key model.
flake-parts Remove The design exposes plain Nix entrypoints instead of flake outputs.
gen-flake Remove It is coupled to the current generated flake-parts module flow.
gen-schema Remove Direct data validation is simpler and benchmarked eval savings were not meaningful.
home-manager Do not add Add only if user-level activation becomes a clear requirement.

CI Test Plan

CI should call plain Nix entrypoints. It should validate graph correctness cheaply on every change and reserve full system builds for representative hosts or cache workflows.

Fleet checks

  • All host owners exist.
  • All user and group references exist.
  • All service primary and backup hosts exist.
  • Every host has a public key path.
  • No service uses the same host as primary and backup.
  • No duplicate host features, tags, target hosts, host IDs, non-link-local network addresses, UIDs, user groups, or group members.

Resolver checks

  • Feature imports close recursively.
  • Cycles fail with a readable path.
  • Platform module selection is correct.
  • Routed service features are activated.
  • Service routing is complete and no unrelated hosts receive a routed service.
  • Routed service ports do not conflict per host and transport protocol.

Deployment checks

  • hive.nix evaluates.
  • darwin.nix evaluates.
  • bin/deploy --plan prints selected targets.
  • Darwin hosts are absent from Colmena hive.
  • Deploy selectors cover host names, @all, platform selectors, and tag selectors.

CI commands

nix-instantiate --eval --strict default.nix -A checks.fleet
nix-instantiate --eval --strict default.nix -A checks.featureClosure
nix-instantiate --eval --strict default.nix -A checks.hostFeaturesHavePlatformModules
bin/check
nix-instantiate --parse hive.nix
nix-instantiate --parse darwin.nix
nix-build ci.nix -A plain-eval
shellcheck bin/deploy bin/check

Optional heavier checks

  • Build one NixOS server toplevel.
  • Build one NixOS desktop toplevel.
  • Evaluate one Darwin host without activating it.
  • Run Colmena in build-only mode for selected NixOS hosts.

Known Migration Gaps

These are the missing pieces from the initial plan after comparing it with the current repository state.

Gap Required work
Legacy architecture removal Remove flake.nix, flake.lock, modules/flake/, gen-modules/, and generated schema docs only after plain deploy, package, formatting, and CI workflows cover the same jobs.
Package and wrapper parity Expose package sets and wrappers through plain Nix, and teach lib/features.nix how to consume feature-owned package metadata if that remains part of the design. The old wrapper modules under modules/features/** still contain flake.wrappers, constructFiles, and legacyPackages behavior that must either be ported or intentionally dropped.

Runtime theming Resolve the runtime theme switcher issues currently noted in TODO.md and decide whether runtime-selected assets belong in feature modules, wrapper metadata, or a separate runtime tool.
Docs and user workflow Update feature notes that still describe the gen-schema or flake-wrapper model, and document the plain commands for evaluation, deployment, formatting, and secret editing.

Acceptance Criteria

  • No routine workflow requires nix flake.
  • bin/deploy --on <host> works for NixOS and Darwin hosts.
  • Colmena hive contains only NixOS hosts.
  • Darwin configurations evaluate from darwin.nix.
  • Feature code is colocated by feature name across platforms.
  • Plain package and wrapper entrypoints replace legacy flake wrapper outputs.
  • Darwin feature behavior is audited against the old flake modules and either ported or intentionally documented as dropped.
  • Service primary and backup routing is validated and visible as host.services.
  • Service-owned secrets are declared by feature metadata rather than hard-coded top-level service names.
  • Agenix secrets remain encrypted in the repo and decrypt on target activation.
  • CI can validate fleet graph, feature resolution, hive evaluation, Darwin evaluation, formatting, and static checks.
  • The legacy flake and generated module trees are removed after parity checks pass.

Open Risks

Darwin deployment is custom. The top-level deploy script must treat Darwin activation as a first-class path and should include dry-run/build-only modes before any remote activation logic. The current script activates Darwin builds locally and does not yet use targetHost for remote Darwin targets.
Wrapper modules may still be eval-heavy. Prior timing showed flake-parts/gen-flake/gen-schema were not the dominant eval cost. After migration, focus profiling on NixOS modules, wrappers, and package overlays.
Feature parity is the main removal blocker. The plain features cover the active Linux fleet, but the old flake module tree still contains package, wrapper, and Darwin behaviors that need a deliberate port-or-drop decision before deletion.
